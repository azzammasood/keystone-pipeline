# Phase 6 review: metadata, lineage and observability

Independent review by a fresh Claude Code subagent (read-only, no Docker, no network), dated
2026-10-21. Scope: `git diff f92a2f3..HEAD` (uv.lock and generated `metadata/contracts/*.yaml`
only spot-checked). Checked: `src/keystone/lineage/`, `src/keystone/telemetry/`,
`src/keystone/export/`, the new and wrapped CLI commands, `config/metadata.yml`, the compose
`lineage`/`obs`/`datahub` profiles, the Grafana dashboard, `contracts/pipeline_metrics.schema.json`,
the CI `metadata` job and `parity.yml`, ADR-031 to ADR-035 and the PROGRESS rows dated
2026-10-21. I compared those claims with local `data/telemetry/runs.jsonl` (37 records),
`data/metrics/pipeline_metrics.json`, `metadata/lineage.json` and `metadata/catalog.json`.
Ran `uv run ruff check .` (clean), `uv run mypy` (clean, 49 files) and
`uv run pytest tests/test_lineage.py tests/test_metadata.py -q` (20 passed). Confirmed by the data:
103 nodes, 118 edges, 256 column edges, 61 unresolved inputs, 19/19 models, 483/483 columns,
44/44 datasets, 15 engines, DataHub dbt 451, iceberg 261, kafka 6 and 57 assertions. Privacy:
no logins, emails or person-level values in `metadata/*.json`, the contracts or the DataHub
aspects. The owner is the `keystone-maintainers` group, and every published dataset is `public`.

## Findings and resolution

| # | Sev | Finding | Resolution |
| --- | --- | --- | --- |
| 1 | major | The field half of the gate ("hourly file to a published export field") is neither met nor enforced. In `metadata/lineage.json`, `gate_path.field` ends at `keystone.staging.stg_gharchive__repo_names#{created_at,repo_id,repo_name}`. It never reaches `silver/gharchive/events` or the hourly file, because dbt-ol cannot resolve `read_parquet` (part of the 61 dropped inputs) and the parser emits table-level lineage only. `metadata export --require-path` (`cli.py`, `if ... not (gate["tables"] and gate["field"])`) only checks that the chain is non-empty. `build_lineage` (`export/catalog.py` l.205-210) always puts `target#col` itself in the chain, so any published table with one column passes. Marquez (`_marquez_missing`) and DataHub (`gate_missing`) check table-level nodes only. PROGRESS ("path ... to a published Iceberg field exists ... in Marquez and in DataHub") overstates this. | Fixed: the rollup's column lineage is derived from its SQL by sqlglot (`lineage/sqllineage.py`) and emitted by the rollup stage, so the chain runs published field, mart, staging, rollup, silver events; the chain is built along the table path (`field_chain_along`) and `--require-path` requires it to reach the table the hourly file is parsed into (`gate_path.complete`); the parse hop stays table level (the file has no schema), stated in ADR-031. Marquez (`/api/v1/column-lineage`) and DataHub (schemaField lineage) now check every field of the chain. PROGRESS states the result per store |
| 2 | major | Several stages log `status: ok` although the command exits 1, because the failure check runs after the `with Stage(...)` block: `lineage datahub` (missing gate datasets or source failures), `warehouse verify` (`if not all(r.matches)` after the block, while `detail.services` already lists spark/flink/trino) and `warehouse build` (docs `generate` and the coverage gate run after the block). `runs.jsonl` and `pipeline_metrics.json` then report a failed run as ok, and `engines()` lists datahub, spark, flink or trino as active with a fresh `last_used`. That breaks tool credibility (a tool listed only with evidence that it ran). | Fixed: the failure checks of `warehouse build` (docs generate, coverage gate), `warehouse verify` and `lineage datahub` run inside the stage, so a failed check is a failed stage and its engines are not `active` |
| 3 | minor | Unmeasured values are published as measured zeros. `totals.bytes_downloaded` is `0` in the local JSON because no `ingest` stage ever ran, yet 151 source hours exist. The schema makes it a required integer, so null is impossible. `quality.checks_passed` likewise falls back to `0` when no contracts or warehouse stage exists (`metrics.py` l.252-253). This breaks "only measured numbers; a value that was not measured is null" (the module docstring). | Fixed: `bytes_downloaded`, `bytes_parsed` and `checks_passed` are null when nothing measured them (schema allows null there); tested |
| 4 | minor | `totals.bytes_parsed` sums `bytes_in` over `EVENT_STAGES = {"ingest","parse"}` (`metrics.py` l.228). For `ingest`, `bytes_in` is the downloaded bytes (`cli.py`, `stage.bytes_in = summary.downloaded_bytes`), even when nothing was parsed (no `--keep` sink), so download bytes are counted as parsed bytes. Separately, `GhArchiveSink` adds `bytes_in` before parsing, so hours that fail on drift still count. | Fixed: `bytes_parsed` sums parse stages' `bytes_in` and ingest's `detail.bytes_parsed` (the sink's parsed bytes), not downloads. The sink adds a file's size only after the hour is written (drift raises before), so failed hours do not count; kept |
| 5 | minor | `history.runs[].status` is `failed` for all three local runs, including the gate run `01a15d0d` that PROGRESS reports as passing. One diagnostic `grafana-check` (06:16:15, 2 mismatches) failed inside that run id. `last_run.stages` also carries five `grafana-check` rows. Re-runs of a check stage under the same `KEYSTONE_RUN_ID` mark the whole pipeline run failed and crowd `last_run`. | Fixed: a run's status and `last_run.stages` use the last attempt of each stage, so a repeated check replaces the earlier one; tested |
| 6 | minor | The Flink stage counts look wrong and are unverified. `rollup-flink-batch` has `records_in == records_out == 2,243,510`. The topic held 2,363,426 records (`produce`), and an aggregating job should not write as many rows as it reads. `versions.flink_last_job_records` picks vertices by the substrings `Source`/`Sink`/`Writer` in chained vertex names and sums `write-records`/`read-records`, so chained or multi-sink vertices can be miscounted. Those numbers go to pipeline_metrics and Grafana as measured. | Fixed: the Flink stage reports no record counts (null); the REST vertex heuristic was removed. Flink's numbers in PROGRESS are durations only |
| 7 | minor | Retention can silently delete events. `retention.compact` gzips each past `YYYY-MM-DD.jsonl` with `gzip.open(..., "wb")`, which overwrites an existing `YYYY-MM-DD.jsonl.gz`. `write_events` files events by `eventTime` day, so late events for a compacted day (`lineage collect` of Flink/Spark files written earlier, or any replay) create a new day file that destroys the archived one on the next compact. The event log is the source of `lineage.json` and DataHub. | Fixed: compaction appends to an existing day archive (gzip member) instead of overwriting it |
| 8 | minor | Grafana can show stale maxima. Panels use `max(last_over_time(...[30d]))`, and the collector exports resource attributes as labels (`resource_to_telemetry_conversion`, `service.version` = keystone version, SDK version), with a 720 h expiry. After a version bump, old and new series coexist and `max` shows the larger, older value. This is the same failure ADR-035 fixed for `service.instance.id`. Stage panels titled "Last run" also show every stage seen in 30 days, while `check-grafana` compares only stages present in `last_run`, so stale bars are never checked. | Fixed: the collector no longer copies resource attributes (versions) into labels, so a version bump keeps the same series; stage panels are titled "Latest run of each stage", which is what they show; `check-grafana` compares the stages of `last_run` |
| 9 | minor | 8 of the 50 values in "50 of 50 equal" compare the JSON with itself: the `keystone_pipeline_*` gauges are exported from the same document by `metrics emit` (`export_gauges`). Only the 42 stage values are independent. ADR-035 and PROGRESS do not separate the two. | Fixed in ADR-035 and PROGRESS: the stage values are independent of the JSON (written by each stage as it ends); the 8 pipeline totals check the transport (OTLP, collector, Prometheus, Grafana) only, and are counted separately |
| 10 | minor | CI does not run the Phase 6 gate. The `metadata` job runs `metadata export` without `--require-path`, has no publish, Marquez or DataHub, and runs `quality contracts` without `--require-all`, so generated contracts whose data is absent in the fixture run (for example `quarantine/osv`, and quarantine GH Archive, which this job does not parse) are skipped silently. "ODCS contract enforced in CI" (9b) holds only for datasets that have fixture rows. Neither gap is logged as deferred. | Fixed: the `metadata` job parses the quarantine fixtures and runs `quality contracts --require-all` (a contract without rows fails); the parity workflow, which publishes to Iceberg, runs `lineage dbt` and `metadata export --require-path` on the fixtures. Marquez and DataHub checks stay local (stack size); logged |
| 11 | minor | The hour-file cap keeps the wrong hours. `_cap_hour_files` (`lineage/graph.py` l.136) sorts ids as strings, and stems are unpadded (`2026-10-19-9` sorts after `2026-10-19-23`), so "the newest 200 hours" is not chronological once the cap applies. | Fixed: hour files sort chronologically (day, then hour as a number); tested |
| 12 | minor | `cost.free_quota` tracks only the disk budget, and its label hard-codes "70% of free disk" instead of reading `disk_budget_fraction` from policy. Other free quotas the project depends on (GitHub Actions minutes on a private repo, for example) are not tracked or listed as unmeasured, although CLAUDE.md requires tracking every free quota. | Fixed: the label reads `disk_budget_fraction` from policy; GitHub Actions minutes are listed with `used_pct: null` (not measurable from a local run) until the production workflow reads them (Phase 10) |
| 13 | nit | `_stage` turns a measured rate of `0.0` into `None` (`if r.records_per_second else None`), while the stage gauge records `0`, so `check-grafana` reports a false mismatch for a stage with zero output. The same applies to `mb_per_second`. | Fixed: a measured 0.0 rate stays 0.0 |
| 14 | nit | `quality-contracts` sets `records_in` = contracts tested (25) and `records_out` = checks passed (559). The resulting `records_per_second` and the records-out panel mix units. `contract_violations` also counts `--require-all` skips as violations. | Fixed: `quality-contracts` records are contract checks (in = run, out = passed); skips without data are `skipped_no_data`, not violations, and fail the run only with `--require-all` |
| 15 | nit | `lineage dbt` reports `outputs_with_column_lineage=34`, which counts START and COMPLETE events (17 models × 2). ADR-031 says 17 models; the CLI label is misleading. | Fixed: the CLI counts models with column lineage in COMPLETE events (`models_with_column_lineage`) |
| 16 | nit | `lineage collect` renames each incoming file to `.collected` before parsing and writing. If canonicalisation or the write fails, those events are never collected again, and `.collected` files are never cleaned up. | Fixed: `lineage collect` renames to `.collecting`, deletes it after the write and renames it back on failure, so events are retried, not lost |
| 17 | nit | `Graph.add` sets a job's `last_run` to the `eventTime` of the last COMPLETE in read order. `read_events` reads all `*.jsonl` before `*.jsonl.gz`, so after compaction `last_run` can be an older time. Use the maximum instead. | Fixed: `last_run` is the maximum event time |
| 18 | nit | `grafana._query` keys frames by the `stage` label only. Two series for the same stage name with different `service` labels (possible, since gauges are labelled by stage and service) overwrite each other in arbitrary order. | Fixed: stage panels and the comparison key on stage and service |

After the fixes (final gate run on the local data, 2026-10-21): the column chain runs from the
published field back to silver `created_at` and the gate requires it; it is present in the
static export, in Marquez (13 nodes, 6 fields) and in DataHub (5 upstream datasets, 5 column
hops with stored fine-grained lineage); Grafana equals the JSON on 50 of 50 values (42 of
them independent stage values); 114 tests pass.
